Claude Code in Action

Llevar Claude Code más allá de la tarea rápida y poder confiar en el resultado: acotar sesiones largas, configurarlo con instrucciones que sí se cumplen, automatizar lo repetitivo y verificar lo que corrió sin que tú mirases.

◈ La tesis del curso en una frase

Cuanta más autonomía le des a Claude, más deliberadas tienen que ser dos cosas: lo que le permites hacer antes (permisos + hooks + instrucciones) y cómo compruebas lo que hizo después (diff, tests como puerta, segunda opinión).

El modelo mental central: tres superficies de instrucción

Casi todo el curso se ordena alrededor de esta decisión. Antes de escribir cualquier regla, pregúntate a quién pertenece.

Interactivo · toca cada superficie

Qué es: guía. No es configuración obligatoria. Claude la lee y decide.

Para qué: convenciones que aplican siempre — dónde van los ficheros, cómo se nombran las cosas, estilo.

Coste: se carga entera, siempre, al arrancar. Cada línea compite con las demás por la atención.

Fiabilidad: Alta pero no garantizada.

Qué es: un procedimiento empaquetado en una carpeta con skill.md: nombre + description que la dispara + los pasos.

Para qué: recetas multipaso ligadas a un tipo de tarea — verificación, release, migración, chequeo pre-PR.

Coste: casi cero. Solo las descriptions viven en contexto hasta que la skill hace falta.

Fiabilidad: Alta pero no garantizada — sigue siendo una instrucción.

Qué es: código determinista que se ejecuta en un punto fijo del bucle. No es una petición: es un cortafuegos.

Para qué: reglas que no se pueden saltar — "nunca push a main", "los tests corren antes de terminar el turno", "redacta secretos de los comandos".

Coste: tienes que escribirlo y mantenerlo.

Fiabilidad: Garantizada.

Si saltarse la regla no es aceptable, no la dejes en manos de "seguir instrucciones".

Steer the Work Lección 1 ▶ Vídeo original

Dirigir sesiones largas

Una tarea corta es fácil: pides, trabaja, compruebas. Un refactor de doce ficheros son horas — y cuanto más tengas que corregirlo sobre la marcha, más se alarga.

◈ Dos hábitos, todo el capítulo

1. Acota el trabajo antes de que empiece. 2. Dirígelo mientras corre.

Interactivo · las 5 herramientas de una sesión larga

Acota primero con plan mode

Antes de que escriba una línea, que presente un plan. En plan mode Claude investiga en solo lectura: lee el código, decide qué cambiar y te entrega el plan a revisar.

  • Léelo de verdad, no lo hojees.
  • Cuanto más completo el plan, menos sorpresas durante la ejecución.
  • Si falta algo, pídele que lo añada exactamente donde lo quieras.
✓ Por qué compensa

Iterar sobre un plan es mucho más rápido que dejarlo correr, cruzar los dedos y luego limpiar el destrozo.

Compact — tu volante del contexto

Resume la conversación, usa el resumen como contexto nuevo y borra los mensajes viejos. Libera ventana de contexto para que Claude pueda seguir.

⚠ El riesgo

Que el resumen tire algo importante y Claude derive del rumbo.

Por eso: nunca /compact a secas. Lo que escribas detrás del comando moldea qué conserva el resumen.

/compact Focus on the --version flag implementation

Ejemplo: terminaste de depurar hace rato y ahora solo te importan unos cambios de API. Dilo.

Rewind — corregir el rumbo sin pelear

Cuando Claude coge el camino equivocado no hace falta que te prompt-ees la salida. Rewind te lleva al último checkpoint.

ℹ Dato de examen

Cada prompt del usuario crea un checkpoint. Abrir el menú: Esc Esc (doble toque) con el prompt vacío.

OpciónQué haceCuándo
Restore code and conversationRevierte ambos a la vezVuelta atrás limpia
Restore conversationSolo el chatEl código está bien, la charla no
Restore codeSolo los ficherosQuieres conservar el razonamiento
Summarize from hereResume todo lo posterior al checkpointHubo una conversación lateral y quieres liberar espacio
Summarize up to hereResume todo lo anteriorFase larga de preparación que comprimir, manteniendo intacta la implementación

Goal — describe el "hecho", no los pasos

Fija una condición de finalización. Claude sigue trabajando entre turnos hasta que un evaluador rápido confirma que se cumple. No para la primera vez que cree haber terminado.

/goal all tests in src/billing pass, and the type checker reports zero errors

/goal clear      # cancelar
⚠ Restricción clave

El evaluador solo lee el transcript. Tu condición tiene que ser comprobable desde la salida que Claude realmente produce — p. ej. el resultado de un test run. "Que el código sea elegante" no vale.

Loop — sondear algo externo

Ejecuta un prompt a intervalos entre turnos, fijo o autoregulado. Sirve para tirar de algo externo (un run de CI, un deploy) y actuar cuando cambia el estado. Se para con Esc.

Worktrees — un volante por coche

La metáfora de dirigir asume un volante en un coche. Varios agentes sobre el mismo repo serían dos volantes en un coche: dos sesiones peleándose por los mismos ficheros acaban en conflictos.

Con worktrees cada sesión recibe su propio árbol de ficheros independiente. No pueden pisarse. Al salir de una sesión, un worktree limpio se elimina automáticamente.

✓ Fichero que hay que conocer

.worktreeinclude en la raíz del repo lista los ficheros ignorados por git que se deben copiar a cada worktree. Perfecto para un .env o una config local que necesitas en todos pero no quieres versionar.

◈ Los cinco hábitos
  1. Acota el trabajo primero, luego dirige.
  2. Dirige la compactación para que el resumen conserve lo que importa.
  3. Usa el menú rewind para corregir cuando derive.
  4. Fija un goal cuando sepas describir mejor el "hecho" que los pasos.
  5. Ejecuta trabajo paralelo en worktrees.

Un CLAUDE.md que se cumple

La trampa que atrapa a casi todo el mundo: el fichero no para de crecer. Un problema → una regla. Otro problema → otra regla. Acabas con un muro de texto y Claude empieza a ignorar partes.

◈ Eso no es un bug de Claude, es cómo funciona el fichero

CLAUDE.md no es configuración obligatoria: es guía. Cada línea compite con todas las demás por la atención de Claude. Cuanto más largo, más compite consigo mismo y menos fiablemente se sigue cualquier regla concreta.

El objetivo no es escribirlo todo. Es mantenerlo apretado. Cuanto más magro el fichero, más lo cumple Claude.

Primero: ¿es CLAUDE.md la herramienta correcta?

Hay reglas que son guía y reglas que son líneas rojas. Son dos trabajos distintos.

Toma "nunca hagas push a main". Si eso va en CLAUDE.md, estás esperando que Claude lo lea y lo respete. La mayoría de las veces lo hará. Pero "la mayoría de las veces" no basta para algo tan peligroso.

✓ La regla dura va a un hook PreToolUse

Un hook es código que corre antes de que Claude actúe y puede bloquear la acción. Aunque Claude intente el push, el hook lo para. Eso es cumplimiento real, no una petición educada. → Ver capítulo 5

Las cuatro ubicaciones

CLAUDE.md no es un único fichero. Hay cuatro sitios donde puede vivir, y Claude carga los cuatro al arrancar. Nada se descarta: se apilan.

Interactivo · toca cada capa

Lo controla tu equipo de plataforma a nivel de organización. No lo puedes excluir, así que la política corporativa siempre está en juego.

Tus preferencias personales. Te siguen a todos los proyectos de tu máquina.

El fichero que compartes con tu equipo, versionado en el repo. Es el que suele engordar.

Ignorado por git. Tus notas para este repositorio y nadie más.

Se pasa por alto y es muy útil: estás refactorizando en tu rama y quieres que Claude tenga presentes ciertas decisiones arquitectónicas mientras trabajas. Eso no va en el fichero compartido, donde afectaría a todo el equipo.

Partir un fichero grande con imports

Cuando el fichero de proyecto se alarga, pártelo con la sintaxis path-to-file:

@.claude/conventions/code-style.md
@.claude/conventions/testing.md
@.claude/conventions/workflow.md
⚠ Es fácil llevarse la idea equivocada

Al arrancar, Claude expande los ficheros importados inline, justo donde los referenciaste. Los imports ayudan a organizar, pero todo se carga igualmente por adelantado. No reducen el contexto que Claude tiene que leer.

La redacción es lo que hace que una regla pegue

Una vez decidido que la regla pertenece a CLAUDE.md, que Claude la obedezca depende de cómo la formules. La mayoría fallan por vagas.

Interactivo · reescribe la regla
✗ Vago

"Follow best practices for API routes."

✓ Específico

"Put new API routes in src/api/handlers, one per file."

El listón: si tú no puedes comprobar si se cumplió, Claude tampoco. Debes poder mirar el resultado y saber al instante si se hizo bien.

✗ Deja la puerta abierta

"Don't use default exports."
Vale… ¿y entonces qué?

✓ La cierra

"Use named exports, not default exports."

Cuando prohíbas algo, di qué hacer en su lugar. Si no, dejas hueco a la interpretación.

IMPORTANT y YOU MUST sí suben la prioridad de una regla — pero solo en relación a lo que está más callado a su alrededor.

⚠ Si todas las reglas gritan…

…ninguna destaca, y el énfasis deja de significar nada.

Trátalo como un presupuesto: gástalo en las dos o tres reglas que de verdad duelen cuando se rompen. El resto, a volumen normal.

Mantén el fichero bajo revisión

Tu CLAUDE.md nunca está terminado. Trátalo como código vivo que se sigue editando.

Cuando Claude haga algo mal, no suspires y lo arregles a mano. Trátalo como un bug report contra tu CLAUDE.md.

Puedes decírselo directamente — "add that to the CLAUDE.md file" — y escribe la regla por ti. Así el fichero mejora cada vez que algo sale mal.

◈ Conclusión

Trata tu CLAUDE.md como código de producción: si no puedes justificar una línea, bórrala.

  1. Mueve las reglas duras a hooks, donde sí se aplican.
  2. Organiza ficheros largos con imports (recordando que no reducen contexto).
  3. Haz cada regla específica y comprobable, y nombra el reemplazo.
  4. Gasta el presupuesto de énfasis en las pocas reglas que importan.
  5. Revísalo cada vez que Claude se equivoque.

Skills de verificación

Las skills automatizan trabajo repetido. De todas las que puedes construir, la de verificar tu propio trabajo es la primera que merece la pena.

Por qué esta va primero

Piensa en cómo compruebas normalmente el trabajo de Claude: le pides un refactor, termina, y entonces tú tienes que acordarte de revisar. Quizá le pides que lance los tests. Quizá lees el diff.

⚠ El problema

La comprobación depende de que tú te acuerdes de pedirla. Te lo saltas una vez y cuela código malo.

Una skill de verificación elimina esa dependencia:

La forma de la skill · toca cada paso

Pides un refactor. Al terminar, el cambio encaja con la description de la skill → la skill se dispara sin que tú la pidas. La description es el disparador.

Ejecuta la suite de tests. Siempre la misma, siempre igual.

Lee el diff completo, no solo el resumen de lo que dice haber hecho.

⚠ El paso que casi nadie pone

No basta con ver los tests en verde: un test se puede aflojar en silencio para que pase pase lo que pase. La skill lee el diff y confirma que no se debilitó ningún test solo para que compilase.

Reporta pass o fail, con la evidencia adjunta.

"Hecho" no es "el código parece correcto leyendo el diff". Hecho es que las puertas se ejecutaron y se observaron, con los resultados declarados explícitamente.

◈ Regla del pulgar

Si has tecleado la misma instrucción multipaso dos veces, eso es una skill. Sirve para cualquier procedimiento que tu equipo repita: checklist de release, receta de migración, chequeo pre-PR.

Una carpeta de skill guarda más que instrucciones

Una skill no es solo un skill.md. La carpeta puede llevar más cosas, y eso es lo que la hace potente:

reference.md

Material detallado al lado, enlazado desde skill.md. Claude solo lo lee cuando necesita esa profundidad → tu fichero principal se queda corto.

Scripts (check.sh…)

Claude los ejecuta en vez de cargar su contenido en contexto. La skill lleva su propio utillaje: un script que corre todas las puertas de una vez.

El fichero magro describe qué hacer; los ficheros laterales guardan la profundidad y las herramientas.

Decisor: ¿dónde va esta regla?

Interactivo · responde y te digo la superficie

¿Claude podría saltarse esta regla sin consecuencias inaceptables?

¿Aplica siempre, o solo dentro de un tipo de tarea concreto?

◈ Recapitulación

Una skill es una carpeta con skill.md: un nombre, una description que la dispara y el procedimiento.

Solo las descriptions se cargan en contexto hasta que la skill se necesita de verdad → no hay coste en empaquetar todos los procedimientos que repites.

Empieza por verificación. Súbela a .claude/skills de tu proyecto y todo el equipo hereda el mismo movimiento: el trabajo de todos se comprueba igual, automáticamente, sin que nadie tenga que acordarse de pedirlo.

Modos de permisos

Decidir una vez qué puede ejecutar Claude sin pararse a preguntar, en vez de aprobar acción por acción. Eliges el modo que encaja con el trabajo y le dejas operar al nivel de confianza con el que estés cómodo.

Interactivo · mueve el dial de confianza
← más controlmás autonomía →
ℹ Cómo se cambia

shift+tab cicla los modos del día a día: manual → accept edits → plan → auto. La barra de estado de abajo muestra siempre en cuál estás, así que basta un vistazo para saber qué puede hacer Claude.

Cómo funciona el modo auto

Auto es el modo sin manos. Claude corre solo, pero antes de que cada acción se ejecute, un modelo clasificador aparte la revisa. El clasificador vigila la intención: busca movimientos que escalen más allá de lo que realmente pediste.

✗ Diseñado para bloquear
  • Deploys y migraciones de producción
  • Force push, o canalizar código descargado directo a una shell
  • Enviar datos sensibles a endpoints externos
  • Destruir ficheros que existen para la sesión
✓ Deja pasar
  • Ediciones locales en tu proyecto
  • Instalar dependencias desde tu lock file
  • Peticiones de solo lectura
  • Push a tu propia rama
⚠ El punto ciego del clasificador

Comprueba intención, no corrección. No detecta si el código funciona.

Si pides refactorizar la autenticación y Claude escribe una autenticación rota, el clasificador la deja pasar — porque roto no es peligroso.

◈ El emparejamiento canónico del curso
Auto mode · antes

Vigila lo que Claude intenta hacer mientras corre. Guarda la intención.

Stop hook · después

Confirma que el código realmente funciona cuando Claude termina. Guarda la corrección.

Las salvaguardas del modo auto siguen evolucionando: consulta la documentación para las listas de bloqueo y permitidos actuales.

Don't ask, para runs desatendidos

Es el movimiento correcto siempre que no haya un humano para aprobar prompts: pipelines de CI, jobs programados, lotes nocturnos.

Solo se permiten herramientas pre-aprobadas; lo que esté fuera de la lista se auto-deniega sin prompt. Ese es todo el objetivo: tu pipeline sigue avanzando en vez de colgarse esperando una aprobación que nadie va a dar.

◈ Empareja el modo con el trabajo
  • Auto — modo sin manos. Clasificador (intención) antes + stop hook (corrección) después.
  • Don't ask — pipelines desatendidos donde no hay nadie para aprobar.
  • Bypass permissions — solo dentro de contenedores aislados y VMs.

Hooks

Decirle algo a Claude en CLAUDE.md es una petición, no una garantía. Escribes "always format after editing" y normalmente hará caso. Normalmente. En un run largo que no estás mirando, "normalmente" no basta.

◈ La propuesta

Un hook es código determinista que corre en un punto fijo del bucle, así que puede garantizar comportamiento en vez de esperarlo. Convierte una regla de "Claude suele hacer caso" en "Claude no puede saltársela".

Los eventos del bucle

Claude Code dispara ~30 eventos de hook por sesión. No hacen falta todos: hay un puñado al que recurrirás una y otra vez, y encajan en puntos del bucle agéntico donde querrías intervenir.

Interactivo · el bucle agéntico, toca un evento

Dispara al inicio y prepara el entorno. Usa el source startup si solo lo quieres en arranques frescos.

También es la clave del truco de compactación de más abajo.

Dispara cuando se carga un CLAUDE.md o un fichero de reglas. Muy útil para auditar qué entró realmente en contexto.

Tu primitiva de enforcement. Es la única que puede parar algo antes de que ocurra. Aquí está el poder real del sistema de hooks.

Dispara tras una llamada a herramienta con éxito. Aquí suelen ir el auto-formateo y el auto-lint.

Ojo: la herramienta ya corrió — bloquear aquí llega tarde para impedir la llamada, aunque sí puedes devolver texto a Claude.

Disparan antes y después de la compactación.

Pero si lo que quieres es re-inyectar contexto tras compactar, no es esto lo que buscas → mira la caja roja de abajo.

Dispara cuando Claude quiere terminar su turno. Puedes negarte: "no, no has terminado", si alguna condición no se cumple. Existe SubagentStop para cuando termina un sub-agente.

Es donde vive el hook de tests como puerta.

⚠ La que despista a todo el mundo

Para re-inyectar contexto después de una compactación, NO uses PostCompact. Usa SessionStart con el matcher compact. Ese es el que realmente devuelve su salida a la conversación.

PreToolUse: devolver una decisión como JSON

Aquí está el poder real, porque puede bloquear una llamada antes de que corra. Le hablas a Claude imprimiendo JSON y saliendo con código 0. El campo clave es permissionDecision:

ValorEfecto
allowDeja pasar la llamada
denyPara la llamada
askSe lo devuelve al usuario para que decida
deferCuarto valor, raro: solo en runs no interactivos -p, donde un proceso llamante pausa la herramienta y la reanuda después
 
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "...",
    "updatedInput": {
      "command": "..."
    }
  }
}
⚠ Pega de updatedInput

Reemplaza el objeto de input completo. Tienes que devolver también los campos que no estás cambiando, o los pierdes.

Códigos de salida (hooks que no hablan JSON)

CódigoSignificado
0Éxito. Si stdout es JSON, Claude lo parsea. El texto plano se ignora en la mayoría de eventos — excepto en SessionStart, UserPromptSubmit y UserPromptExpansion, donde el texto plano se añade al contexto. Eso es exactamente lo que hace funcionar un hook preservador de estado.
2Error bloqueante. stderr se le devuelve a Claude como contexto. Es el código de bloqueo en casi todas partes.
otroNo bloqueante. stderr se registra y Claude sigue.
⚠ El fallo clásico: exit 1

exit 1 parece un error, pero NO bloquea. Claude ejecuta el comando igualmente. Si querías parar algo: exit 2, no exit 1.

  • exit 2 puede incluso bloquear Stop — así es como le dices a Claude que no ha terminado.
  • PostToolUse dispara después de que la herramienta ya corrió: bloquear ahí llega tarde.
  • Algunos eventos ignoran el bloqueo por completo — Notification y SessionStart muestran tu stderr y siguen igualmente.

Guardarraíl real: redactar en vez de bloquear

Caso práctico: un guardarraíl PreToolUse sobre la herramienta Bash. El matcher elige la herramienta a vigilar y una cláusula if opcional la acota a un comando concreto.

El movimiento obvio

Devolver deny y parar la llamada peligrosa. Está bien.

El movimiento interesante

Devolver updatedInput para reescribir la llamada.

Claude va a ejecutar un comando que incluye un secreto de aspecto real. El hook lo intercepta, detecta el patrón sk_live_ y lo sustituye por un placeholder antes de que el comando se ejecute.

✓ El resultado

El comando corrió. El trabajo se hizo. El secreto nunca pasó. Esa es la diferencia entre bloquear y redactar — y un hook lo aplica todas las veces.

Preservar estado a través de una compactación

Cuando Claude compacta una conversación larga, tira mucho detalle. Un hook SessionStart con el matcher compact corre justo después. Haz que imprima un resumen corto de los ficheros en los que estabas trabajando: ese texto vuelve al contexto y Claude retoma donde lo dejó en vez de arrancar en frío.

◈ Cierre

Los hooks convierten una regla que Claude suele seguir en una que siempre sigue. Ve más allá del auto-formateo: guarda herramientas con PreToolUse, cierra el turno con Stop y preserva estado a través de un compact. El montaje cuesta algo al principio y se paga la primera vez que pilla algo en un run que ni siquiera estabas mirando.

Routines y modo headless

Cuando ya confías en Claude para una tarea, el siguiente paso es dejar de hacerla a mano. Si es el mismo prompt sobre un disparador recurrente, no deberías tener que lanzarlo tú cada vez.

Interactivo · el espectro de automatización
← construyes menosmás control →

Routines: un prompt guardado que corre en la nube

La forma más directa de automatizar una tarea. Sin script y sin servidor. Empaqueta tres cosas y las ejecuta en la nube cuando se dispara:

① Un prompt

Las instrucciones de qué hacer en cada sesión.

② El repositorio

Sobre el que trabaja.

③ Los connectors

Lo que necesite para llegar a tus datos.

Lo clave: la infraestructura es de Anthropic. No hay máquina tuya encendida toda la noche ni fichero de workflow que mantener. Describes el trabajo una vez y simplemente corre.

Los tres disparadores

  • Cron — p. ej. cada mañana a las 9:00.
  • HTTP POST a su endpoint de API, para que tu propio código lo lance.
  • Evento de GitHub — p. ej. un pull request nuevo.

Buenos candidatos: una auditoría matinal de dependencias, un triador de PRs que se dispara al llegar uno nuevo, un escaneo diario de tus tickets de Sentry para saber qué es más urgente.

Dos formas de crearla

Desde la web

claude.ai/code/routines — nombre, instrucciones, repositorio y disparador.

Desde el terminal

Sin salir de Claude Code, en lenguaje natural:

/schedule daily dependency
  audit at 9am
⚠ Tres límites antes de depender de routines
  1. Son research preview. El comportamiento y los límites van a seguir moviéndose.
  2. Un horario recurrente corre como mucho cada hora. Si necesitas más frecuencia, no es la herramienta.
  3. Cada run arranca desde un clon fresco de tu rama por defecto y solo puede hacer push a ramas con prefijo claude/ (salvo que lo relajes por repo). Es el guardarraíl que impide que un run autónomo reescriba main.

Modo headless: cuando necesitas tu propio entorno

Routines va bien cuando el trabajo cabe en la nube. Pero a veces el job necesita tu entorno, o lógica envolviendo el run.

El núcleo es el flag -p (abreviatura de --print): ejecuta Claude Code como comando one-shot sin UI interactiva. Lee de stdin y escribe a stdout, así que se canaliza como cualquier herramienta de shell.

claude -p "summarize the changes in this diff"
⚠ Lo que se pierde con -p

Se salta el auto-descubrimiento de hooks, skills, plugins, servidores MCP y el fichero CLAUDE.md. Obtienes Claude más las herramientas que permitas explícitamente y nada de lo que el entorno local cargue por su cuenta.

A cambio: el arranque es mucho más rápido.

Salida estructurada

Como headless se canaliza como cualquier herramienta de shell, muchas veces querrás datos estructurados en vez de prosa. Empareja un JSON schema con el formato de salida JSON y Claude restringe su salida a tu esquema. El objeto aterriza en el campo structured_output:

claude -p "Extract the exported function names from src/core/style.js" \
  --output-format json \
  --json-schema '{"type":"object","properties":{"functions":{"type":"array","items":{"type":"string"}}},"required":["functions"]}' \
  | jq '.structured_output.functions'

Automatización multipaso con sesiones

No hay que meterlo todo en un comando. Captura el session_id de la salida JSON y reanuda después:

claude --resume "$(jq -r .session_id /tmp/plan.json)"

Un script arranca el trabajo, otro lo reanuda más tarde con contexto completo. Útil cuando la primera pasada produce un plan y la segunda lo ejecuta.

Runs deterministas para CI

Cuando CI necesita los mismos resultados en cada run, el flag --bare da modo determinista. Es lo correcto dentro de un pipeline donde quieres salida repetible y predecible.

El Agent SDK: Claude Code dentro de tu app

Último escalón del espectro: una librería que embebe Claude Code en tus aplicaciones TypeScript o Python. Ambos lenguajes exponen una función query y las mismas primitivas que la CLI. Le pasas un prompt más opciones:

  • allowedTools — controlar qué puede hacer Claude
  • un system prompt
  • un permission mode

Luego iteras sobre los mensajes que Claude devuelve en streaming y los manejas como tu app necesite. Mismo motor que la CLI, invocable desde dentro de tu producto.

GitHub Actions y Code Review

El mejor sitio para delegar trabajo repetitivo es el pull request: es donde ocurre la revisión, donde aterrizan los cambios y donde vive buena parte del trabajo mecánico.

Interactivo · dos caminos, problemas distintos

Servicio hospedado por Anthropic que revisa tus PRs mediante la Claude GitHub app. Nada que construir ni hospedar: lo activas y empieza a publicar hallazgos como comentarios inline en las líneas que importan.

Activación

Un admin de la organización lo habilita desde los ajustes de admin de Claude Code → sección Code review → botón Configure. Desde ahí instala la Claude GitHub app, elige qué repos vigila y decide cuándo corre:

  • Una vez, al abrir el PR
  • En cada push al PR
  • Solo cuando alguien comenta @claude review

Cómo trabaja

Todo corre en infraestructura de Anthropic. Un conjunto de agentes de revisión analiza el diff contra tu codebase completo, no solo las líneas cambiadas en aislamiento. Publica hallazgos como comentarios inline en las líneas concretas, etiquetados por severidad, con una tabla resumen en el check run.

✓ Lo bueno

Deduplica y rankea los hallazgos. En vez de un muro de nimiedades, lees un puñado de problemas reales que merecen tu atención.

⚠ Sus límites
  • Nunca aprueba ni bloquea el PR. El juicio se queda con un humano: Claude marca, tú decides.
  • No hay autofix gestionado. El servicio solo publica hallazgos.
  • Es research preview, disponible en planes team y enterprise.

Como no hay autofix en el servicio, aplicar un hallazgo es un movimiento local:

/code-review          # revisa un diff
/code-review --fix    # aplica los hallazgos a tu working tree

Flujo: Claude lo encuentra en el PR → tú te lo bajas y lo arreglas en local.

Code Review cubre revisión. Cuando el trabajo va más allá de revisar, usas la GitHub Action: CI a medida — implementar cambios desde un comentario, informes programados, cualquier cosa que normalmente escribirías como workflow. Corre el agente sobre comentarios de PR, jobs programados y cualquier evento de GitHub.

ℹ Setup

Desde dentro de Claude Code, ejecuta /install-github-app (necesitas admin del repo). El slash command te guía instalando la GitHub app y poniendo el secreto con la Anthropic API key.

La action es anthropics/claude-code-action@v1. Inputs que usarás de verdad:

InputDescripción
anthropic_api_keyOpcional
github_tokenPor defecto secrets.GITHUB_TOKEN
trigger_phraseQué escucha en los comentarios. Por defecto @claude
use_bedrock / use_vertexCambiar a esos proveedores
promptLa instrucción del run
claude_argsCadena de argumentos CLI pasados directamente a Claude Code

Workflow que responde a @claude

En .github/workflows/claude.yaml, escuchando comentarios de PR e issues:

- uses: anthropics/claude-code-action@v1
  with:
    anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
    github_token: ${{ secrets.GITHUB_TOKEN }}
    trigger_phrase: "@claude"
    prompt: "Your instructions here"
    claude_args: "--max-turns 5 --model claude-sonnet-5"

Alguien escribe "@claude implement the spec in the linked Linear issue" en un PR y la action lo recoge. Claude hace push de commits y publica comentarios describiendo lo que hizo.

Workflow programado

La misma action sirve para un resumen diario: un trigger cron dispara p. ej. a las 9:00 UTC y Claude publica los resultados. Añade también workflow_dispatch para lanzarlo a mano desde la pestaña Actions, donde puedes ver el progreso paso a paso como cualquier workflow.

Ajustar el run con claude_args

  • --max-turns 5 — tope duro al bucle del agente, para que no corra eternamente.
  • Permission mode — en un job desatendido quieres que no se pare a preguntar, porque no hay nadie para contestar.
  • Allowed tools — dale exactamente lo que necesita y nada más. Para un informe: solo lectura.
◈ ¿Cuál usar?
  • Para revisiones de PR → el camino gestionado. Activa Code Review, deja que publique hallazgos inline y aplica arreglos en local con /code-review --fix.
  • Cuando el trabajo es más que revisar → la action. /install-github-app para el setup, un workflow para menciones @claude, otro para cron, y todo el ajuste fino en claude_args.

Empieza por el servicio gestionado. Pasa a la action en cuanto necesites que Claude realmente haga algo en CI, no solo que comente.

Le diste una tarea a Claude y lo dejaste correr sin mirar cada paso. Ahora dice que ha terminado. Antes de enviar ese trabajo necesitas una forma de comprobar algo que ni siquiera supervisaste.

Verifica en proporción a la cuerda que diste. Cuanto menos miraste, más verificas.
Interactivo · ¿cuánto miraste? Mueve el dial
← lo vi todono había nadie →

Mantén los runs desatendidos en auto mode

Cuando un run va desatendido en el trabajo, usa auto mode, no bypass permissions. En auto mode el clasificador sigue revisando cada acción en busca de peligro: esa red de seguridad merece la pena.

⚠ Pero ten claro qué hace esa red

El clasificador nunca juzga si el código es correcto. Solo marca acciones peligrosas. Tu listón de verificación se queda exactamente donde estaba — y lo fijas según lo no supervisado que fuera el run.

Empieza por el diff, no por el resumen

No empieces por el resumen de Claude sobre lo que hizo. Empieza por el diff.

  1. Ejecuta /code-review para recorrer los cambios y marcar problemas.
  2. Después pon tus propios ojos sobre git diff.
⚠ La trampa

Un resumen ordenado que se lee perfectamente… mientras el diff real tocó un fichero que sinceramente no esperabas que tocara. El resumen no te lo dirá. El diff sí.

Lee qué cambió. Lee primero los ficheros que estaban en el plan, luego busca cualquier cosa fuera de él. Un informe limpio no es prueba de código limpio.

Convierte los tests en una puerta, no en una promesa

La puerta real de un run no supervisado es si los tests pasaron y si Claude realmente los ejecutó o solo dijo que lo hizo. No lo dejes a la confianza: cabléalo como hook para que no pueda saltárselo.

Stop hook

Ejecuta tus tests y se niega a terminar el turno si fallan.

Post-tool-use hook

Hace lint y type check después de cada edición.

◈ El detalle clave es el código de salida

Un hook que sale con exit 2 devuelve el fallo directamente a Claude. Claude lee ese fallo y lo arregla sin que se lo pidas. Y mejor aún: la comprobación dispara en cada run, te acuerdes o no de pedirla.

Consigue una segunda opinión en frío

La revisión por sub-agente que harías antes de un PR sirve también aquí. Apúntala a un run no supervisado: abre una sesión o sub-agente fresco y que revise el código cambiado sin memoria de cómo se construyó.

Como no tiene interés en el enfoque, pilla las cosas de las que el run original se autoconvenció. Un segundo revisor con ojos frescos encuentra lo que el autor racionalizó.
◈ Juntándolo todo
  • Lee el diff tú mismo.
  • Convierte los tests en un hook que cierre el turno.
  • Verifica los runs headless por su resultado JSON y su exit code.
  • Consigue una segunda opinión en frío en cualquier cosa que importe.

Con eso, "Claude lo hizo mientras yo no miraba" deja de ser un acto de fe.

Plugins

Un setup en el que confías vale mucho más cuando todo tu equipo lo ejecuta. El problema es moverlo: construyes un buen directorio .claude con skills, subagentes y hooks… ¿y luego qué? Todos copiando y pegando ficheros entre máquinas, esperando que sigan sincronizados.

◈ Qué es un plugin

Una unidad instalable. Empaqueta todo lo que si no compartirías a mano: skills, subagentes, hooks y configs de servidores MCP, más la cola larga — servidores LSP, monitores en segundo plano, temas y una porción de settings.json. Una versión, una instalación.

Instalar y compartir

Instalación directa
/plugin install org@plugin

Claude Code lo instala y te dice que ejecutes /reload-plugins para aplicar el cambio.

Marketplace de equipo (mejor)
/plugin marketplace add
  your-org/claude-plugins

Una vez añadido, toda instalación posterior se resuelve a través de él: descubrimiento centralizado, seguimiento de versiones y actualizaciones en un solo sitio.

Puedes explorar lo disponible desde la pestaña Discover, que lista los plugins de tus marketplaces.

Lee antes de instalar

⚠ La parte que más importa de todo el capítulo

Un plugin ejecuta código en tu máquina, con tus privilegios. Sus hooks disparan en cada llamada a herramienta que haga match.

Si instalas un plugin por sus skills, también te llevas sus hooks PreToolUse y Stop, los hayas leído o no. Un plugin de la comunidad podría traer un Stop hook que llame a un endpoint de red cada vez, y nada en tu configuración te avisaría.

No es razón para evitar plugins. Es razón para mirar primero. Antes de instalar, revisa los detalles: Claude Code te muestra qué va a instalar y estima el coste de contexto, junto con un aviso claro de que Anthropic no controla lo que hay dentro de plugins de terceros.

Marketplace de la comunidad

El formulario de envío in-app publica ahí tras la revisión automatizada de Anthropic.

Marketplace oficial

Se cura en una vía separada.

Revisado no es lo mismo que confiable. La revisión automatizada pilla algunas cosas, no todas.

Los componentes corren junto a los tuyos

Un plugin no sobrescribe tu configuración: sus componentes corren en paralelo. Eso es mayormente bueno, pero tiene consecuencias.

Interactivo · qué pasa con cada componente

Se apilan. El PreToolUse del plugin y el tuyo disparan ambos en cada llamada a herramienta. Ninguno reemplaza al otro. Exactamente por eso lees los detalles primero.

Van con namespace bajo el nombre del plugin, así que nunca chocan con los tuyos.

Un plugin puede traer un settings.json, pero solo uno estrecho: Claude Code honra únicamente dos claves — las de agent y subagent status line.

⚠ La clave agent merece una pausa

Ponerla promueve uno de los subagentes del plugin al hilo principal, junto con su system prompt, sus restricciones de herramientas y su modelo. Es decir: habilitar el plugin puede cambiar cómo se comporta Claude Code por defecto. Otra razón para mirar antes incluso de encenderlo.

Una vez instalado, ves todo lo que añadió, lo gestionas y lo desinstalas desde el panel de plugins.

Empaquetar el tuyo

La buena noticia: no hay que reestructurar nada. Un plugin usa la misma forma .claude que ya usas, y Claude Code descubre los componentes por convención:

  • Una carpeta por skill.
  • Un fichero markdown por subagente bajo agents.
  • hooks/hooks.json y .mcp.json en la raíz del plugin.

El manifiesto (opcional)

Vive en .claude-plugin/plugin.json:

{
  "name": "svg-splitter-review",
  "version": "0.1.0",
  "description": "Reviews the SVG Splitter repo",
  "author": {
    "name": "Lewis Menelaws"
  }
}

Sin él, Claude Code descubre igualmente tus componentes por convención de directorios. Pero dos detalles importan:

  • name es el único campo obligatorio. Pone namespace a tus skills como company-name:skill-name, evitando colisiones con las de cualquier otro.
  • Versiona como cualquier otra dependencia. Es lo que hace funcionar actualizaciones y seguimiento de versiones en el equipo.
◈ Dos reglas cubren casi todo
  • Cuando uses plugins: lee antes de instalar. Ejecuta código con tus privilegios — mira sus hooks, agentes y servidores MCP primero.
  • Cuando construyas uno: empaqueta tu .claude en cuanto funcione. Un manifiesto, una instalación.

Una unidad instalable, y el setup en el que confías llega a todo tu equipo.
