MCP: Advanced Topics

Lo que MCP puede hacer más allá de exponer herramientas: que el servidor le pida cosas al cliente. Y por qué esa dirección de comunicación es exactamente la que se rompe al desplegar.

◈ El curso entero en una idea

Las tres capacidades del primer bloque —sampling, notificaciones y roots— parecen temas sueltos. No lo son: las tres necesitan que el servidor inicie una petición hacia el cliente.

STDIO da esa dirección gratis. HTTP no. Todo el segundo bloque es la historia de ese apaño y de los dos flags que lo desmontan.

Servidor → clienteLección 1

Sampling

Técnica que permite a un servidor MCP pedirle al cliente que genere texto con un modelo de lenguaje, en vez de acceder el servidor directamente a un LLM.

El problema que resuelve

Un servidor MCP que quiera usar un LLM tendría que gestionar claves de API, gestionar autenticación y pagar los costes de tokens.

◈ Lo que hace sampling

Traslada la responsabilidad del acceso al LLM del servidor al cliente. El servidor no necesita ninguna de esas tres cosas.

Arquitectura

El flujo, en cuatro saltos
Servidor MCP

Crea la petición de mensaje dentro de una llamada a herramienta

→create_message()
Cliente MCP

La recibe en su sampling callback

Cliente MCP

Llama al LLM con sus propias credenciales

→SDK del LLM
LLM

Genera el texto

Servidor MCP

Recibe el texto y hace lo que quiera con él

←CreateMessageResult
Cliente MCP

Devuelve el texto generado

✓ Beneficios
  • Elimina la complejidad de integrar un LLM en el servidor
  • Quita el requisito de claves de API del servidor
  • Evita el uso no autorizado de tokens en servidores públicos
◈ Caso de uso principal
  • Servidores MCP accesibles públicamente que necesitan capacidades de LLM
  • …sin acceso directo a uno
  • …ni los costes ni los problemas de seguridad asociados

Servidor → clienteLección 2

Notificaciones de log y progreso

Capacidad del servidor que da feedback en tiempo real durante la ejecución de una herramienta. Sin esto, una llamada que tarda es una caja negra.

Qué evita

Que el usuario crea que la llamada se ha atascado o ha fallado.

Qué da

Visibilidad sobre operaciones largas, en tiempo real.

ℹ Es opcional

Puedes prescindir de ella. Es puramente mejora de UX, no cambia lo que la herramienta hace.

Los dos lados

Interactivo · servidor y cliente
  • Las funciones de herramienta reciben automáticamente un argumento Context como último parámetro. No hay que registrarlo.
  • El objeto Context ofrece info(), warning(), debug() y error() para logs, y report_progress() para el avance.
  • Llamar a esos métodos envía mensajes al cliente automáticamente.

Dos callbacks separados… y aquí está el detalle que se confunde: se registran en sitios distintos.

CallbackDónde se pasaPor qué
loggingClientSession(...)Es de la sesión entera
progresocall_tool(...)Es de una llamada concreta

Los callbacks deciden cómo mostrar la información: terminal, interfaz web, lo que sea.

Servidor → clienteLección 3

Roots

Forma codificada de que un usuario conceda a un servidor acceso a ficheros y carpetas concretos.

El problema sin roots

El usuario dice "convierte bikin.mp4". Claude no puede localizar el fichero en un sistema de ficheros complejo sin la ruta completa. Y exigirle al usuario que escriba rutas completas es incómodo.

◈ Root

Fichero o carpeta al que el usuario concede permiso de acceso por adelantado — normalmente vía argumentos de línea de comandos al arrancar el servidor. Su URI debe empezar por file://.

Las tres herramientas del ejemplo

HerramientaQué hace
ConvertVideoLa herramienta original
ReadDirectoryLista ficheros y carpetas de un directorio
ListRootsDevuelve los roots disponibles
① Control de permisos

Limita el acceso del servidor solo a las zonas autorizadas.

② Descubrimiento autónomo

Claude puede buscar por los roots disponibles para encontrar ficheros, sin que el usuario dé la ruta completa.

⚠ La limitación clave del capítulo

El SDK de MCP no impone las restricciones de root automáticamente. El desarrollador del servidor tiene que implementar las comprobaciones de acceso a mano.

Escribe algo como is_path_allowed() y llámala en todas tus herramientas antes de tocar nada.

ℹ ListRoots es opcional

Como alternativa puedes meter la lista de roots directamente en el prompt. El patrón de herramienta permite a Claude consultar dinámicamente los roots cuando le hagan falta.

ProtocoloLección 4

Tipos de mensaje JSON

La comunicación en MCP son mensajes JSON entre clientes y servidores. Cada tipo tiene un propósito distinto.

Interactivo · las dos categorías

Siempre van juntos: a cada petición le corresponde un resultado.

  • call_tool_request + call_tool_result
  • initialize_request + initialize_result

Eventos que no necesitan respuesta.

  • progress_notification
  • logging_message_notification
  • tool_change_notification

Clasificación por dirección

  • Client messages — los envía el cliente MCP al servidor.
  • Server messages — los envía el servidor MCP al cliente.
◈ La frase bisagra del curso

Los servidores pueden enviar mensajes AL cliente: hay server requests y server notifications.

Esa capacidad direccional se convierte en la limitación crítica del transporte StreamableHTTP.

Todo lo de los capítulos 1 a 3 son mensajes en esa dirección. Todo lo del 6 al 8 es lo que pasa cuando esa dirección deja de ser gratis.

Dos detalles

El esquema

Un fichero TypeScript en el repo de la especificación: schema.ts. No es código ejecutable, solo descripciones de tipos por comodidad.

La estructura

Formato JSON-RPC, con campos method, params e ID.

TransportesLección 5

El transporte STDIO

Transporte = el mecanismo para mover los mensajes JSON entre cliente y servidor. En STDIO, el cliente lanza el servidor como un proceso aparte y hablan por los flujos estándar.

Bidireccional por naturaleza
Cliente

escribe en el stdin del servidor

→stdin
Servidor

lo lee de su stdin

Cliente

lo lee del stdout del servidor

←stdout
Servidor

escribe en su stdout

✓ La ventaja
  • Comunicación bidireccional: cualquiera de los dos puede iniciar una petición en cualquier momento
  • Por eso sampling, notificaciones y roots funcionan sin ningún apaño
✗ La limitación
  • Solo funciona cuando cliente y servidor corren en la misma máquina física

Secuencia de inicialización obligatoria

  1. Initialize request — cliente → servidor
  2. Initialize result — servidor → cliente
  3. Initialize notification — cliente → servidor, no requiere respuesta

Los tres tipos de mensaje

Tipo¿Espera respuesta?
RequestsSí
NotificationsNo
ResultsSon la respuesta a un request
El transporte HTTP tiene limitaciones sobre las peticiones iniciadas por el servidor que STDIO no tiene.

TransportesLección 6

El transporte StreamableHTTP

Permite la comunicación sobre HTTP, habilitando alojar el servidor remotamente — al contrario que STDIO, que exige que ambos estén en la misma máquina.

✓ La ventaja

Alojamiento remoto. Los servidores pueden ser accesibles públicamente en una URL como mcpserver.com, lo que amplía enormemente lo que se puede hacer con un servidor MCP.

La limitación crítica

HTTP solo va en un sentido
Cliente

pide sin problema

→petición HTTP
Servidor

responde

Cliente

¿en qué dirección? ¿es siquiera accesible?

⇠no hay vía
Servidor

quiere iniciar una petición

⚠ Por qué exactamente
  • El servidor no conoce la dirección del cliente.
  • El cliente puede no ser accesible públicamente.

Qué se ve afectado

Todos los tipos de mensaje que necesitan comunicación servidor → cliente. Es decir: exactamente todo el primer bloque del curso.

✗ En riesgo
  • Peticiones de sampling → cap. 1
  • Listado de roots → cap. 3
  • Notificaciones de progreso → cap. 2
  • Notificaciones de logging → cap. 2
◈ Los dos flags
  • stateless HTTP — por defecto false
  • JSON response — por defecto false
  • Ponerlos a true reduce la funcionalidad
⚠ El fallo de despliegue clásico

La aplicación funciona perfectamente en local con STDIO y falla al desplegarla con HTTP, por estas restricciones de mensajería. Es el error que este capítulo existe para prevenir.

Hay solución: StreamableHTTP tiene apaños para la comunicación servidor → cliente — pero con condiciones.

TransportesLección 7

StreamableHTTP en profundidad

El apaño: usar server-sent events (SSE) para que el servidor pueda hacer streaming de mensajes hacia el cliente.

Las respuestas SSE habilitan comunicación bidireccional sobre HTTP manteniendo las conexiones abiertas y enviando mensajes individuales del servidor al cliente.

Flujo de inicialización

Interactivo · los cuatro pasos

El cliente envía la petición initialize.

El servidor responde con el resultado más la cabecera con el MCP session ID.

Session ID = identificador aleatorio asignado durante la inicialización, incluido en todas las peticiones posteriores como cabecera HTTP.

El cliente envía la notificación initialized con el session ID.

El cliente, opcionalmente, hace una petición GET con el session ID para establecer la conexión SSE.

Es esta conexión la que stateless_http desactiva.

Las dos conexiones SSE

El punto que hay que retener del capítulo.

ConexiónVidaPara qué
SSE de larga duraciónpersistentePeticiones iniciadas por el servidor — sampling, notificaciones
SSE de corta duraciónse cierra solaRespuestas a una llamada a herramienta concreta; se cierra automáticamente tras el resultado

Enrutado de mensajes

MensajeVa por
Notificaciones de progresoconexión larga
Mensajes de logging + resultados de herramientaconexión corta, atada a esa petición
⚠ Detalle contraintuitivo

Progreso y logging no viajan por la misma conexión, aunque los emitas desde la misma función de herramienta con el mismo ctx.

◈ La limitación clave

Poner ciertos flags a true rompe el apaño, lo que hace que StreamableHTTP sea complejo de entender y de usar correctamente.

Estado: los dos flags

Los flags que rompen el apaño SSE. Entender qué apagan es lo que evita el fallo de despliegue.

Interactivo · enciende los flags y mira qué se rompe

Flag 1 · stateless_http

Se pone a true cuando el servidor MCP necesita escalado horizontal entre varias instancias con un balanceador de carga.

ℹ Por qué haría falta

Una sola instancia no puede con mucho tráfico. El escalado horizontal usa varias copias del servidor + un balanceador que reparte las peticiones aleatoriamente.

⚠ El problema sin stateless

El cliente necesita dos conexiones: un GET SSE para las peticiones servidor → cliente, y un POST para las de cliente → servidor.

El balanceador puede mandar cada una a una instancia distinta. Si una herramienta en el Servidor A necesita hacer sampling, tiene que salir por la conexión GET SSE abierta contra el Servidor B — y eso exige una coordinación compleja.

Qué pasa con stateless_http = true

  • No se asignan session IDs a los clientes.
  • El servidor no puede rastrear clientes individuales.
  • Se desactiva la vía de respuesta GET SSE → el servidor no puede enviar peticiones al cliente.
  • Elimina sampling, logging de progreso y suscripciones a recursos.
  • No hace falta inicialización del cliente: se salta la petición initialize y su notificación.
  • Reduce el tráfico del servidor.

Es un intercambio directo: escalabilidad a cambio de las capacidades servidor → cliente.

Flag 2 · json_response

Desactiva las respuestas por streaming en las peticiones POST.

  • Las respuestas POST devuelven solo el resultado final, en JSON plano.
  • Sin mensajes intermedios por streaming.
  • Sin sentencias de progreso ni de log durante la ejecución.
  • El cliente espera a que la herramienta termine por completo antes de recibir nada.

◈ La conclusión del curso

Ambos flags cambian significativamente el comportamiento del servidor. Usa en desarrollo el mismo transporte que vas a usar en producción, para evitar problemas al desplegar.

Lo que se rompe al desplegar no es tu código: es la dirección de comunicación que tu código daba por hecha.
