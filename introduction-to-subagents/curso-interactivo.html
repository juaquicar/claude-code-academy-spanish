Lección 1 ▶ Vídeo original

¿Qué son los subagentes?

Asistentes especializados a los que Claude Code puede delegar. Cada uno corre en su propia ventana de contexto, hace su trabajo y devuelve un resumen al hilo principal.

Por qué importan

Cada vez que hablas con Claude Code añades a la ventana de contexto principal: cada llamada a herramienta, cada fichero leído, cada resultado de búsqueda. Ese espacio es finito — y cuando se llena, Claude empieza a perder el hilo de lo anterior.

Los subagentes lo resuelven levantando una ventana de contexto separada. El subagente recibe exactamente dos cosas:

① Un system prompt propio

Desde tu fichero de configuración. Define su rol y su comportamiento.

② Una descripción de tarea

Escrita por el agente padre a partir de lo que pediste.

A partir de ahí trabaja solo: lee ficheros, busca, edita código. Cuando termina, solo el resumen vuelve — y la conversación completa del subagente se descarta.

⚠ El trato, explícito
✓ Ganas
  • Contexto principal limpio
  • La respuesta sin el ruido del viaje
✗ Pierdes
  • Visibilidad de cómo llegó ahí
  • El detalle intermedio, comprimido

✓ El resultado

Más allá de los integrados puedes crear los tuyos, con system prompt y acceso a herramientas a medida: un revisor de código, un escritor de tests, un generador de documentación.

◈ Tres beneficios
  1. Trocean el trabajo en piezas enfocadas.
  2. Mantienen limpio el contexto principal aislando el trabajo intermedio.
  3. Devuelven justo lo que necesitas, como resumen conciso.

Cuanto menos ruido en tu contexto principal, más largo y más eficaz puede ser tu trabajo.

Crear un subagente

Un subagente propio es un fichero markdown con frontmatter YAML que le dice a Claude cuándo usarlo y cómo debe comportarse.

Interactivo · los 5 pasos de /agents

El slash command /agents abre la interfaz de gestión → Create new agent. Primero, el alcance:

Project-level

Solo disponible en el proyecto actual.

User-level

Compartido entre todos los proyectos de tu máquina.

Puedes escribir la configuración a mano, pero lo recomendado es dejar que Claude la genere.

Describes qué quieres que haga el subagente y Claude produce el name, la description y el system prompt a partir de tu descripción.

Categorías disponibles: read-only, edit, execution, MCP y other.

✓ Piensa en lo que realmente necesita

Un revisor de código probablemente no necesita edit tools — debe leer y analizar, no cambiar. Aunque sí puede interesar dejarle execution tools activas, para que identifique más fácilmente los cambios pendientes.

ModeloCuándo
HaikuTareas rápidas y ligeras
SonnetBuen término medio entre velocidad y profundidad
OpusAnálisis complejo
InheritEl modelo que corra tu conversación principal

Aparece en la interfaz para que sepas de un vistazo qué subagente está activo. Detalle pequeño, pero ayuda cuando tienes varios corriendo.

Al terminar, se guarda en .claude/agents/tu-agente.md. Juega con los campos y mira cómo cambia:

◈ El cuerpo del markdown es el system prompt

Todo lo que hay bajo el frontmatter YAML. Ahí le das las instrucciones: en qué centrarse, cómo analizar y cómo reportar los hallazgos de vuelta al agente principal.

Un system prompt bien escrito es la diferencia entre un subagente útil y uno que no pilla el punto. Sé específico sobre qué debe buscar y cómo estructurar su salida.

Que Claude lo use automáticamente

Incluye la palabra proactively en el campo description:

description: Proactively suggest running this agent after major code changes...

También puedes añadir conversaciones de ejemplo a la description, para que Claude entienda escenarios concretos. Cuanto más concretos los ejemplos, mejor sabe cuándo delegar.

⚠ Si no se dispara cuando esperas…

El problema está en la description, no en el system prompt. Vuelve ahí y añade ejemplos más específicos y escenarios de disparo. Pruébalo haciendo cambios de código y pidiéndole a Claude que los revise.

Diseñar subagentes eficaces

Un subagente mal configurado divaga, corre demasiado tiempo o produce una salida que el agente principal no puede usar. Los arreglos son cuatro.

◈ El dato que casi nadie conoce

El name y la description de cada subagente disponible se incluyen en el system prompt del agente principal. Así decide cuál lanzar y cuándo.

Y hay un segundo papel: cuando el agente principal lanza un subagente, escribe un prompt de entrada — y usa la description como guía para escribirlo. La description no controla solo cuándo corre: moldea lo que se le dice que haga.

Interactivo · la misma description, dos prompts de entrada

Description: "Use this agent to review code."

Prompt de entrada que escribe el principal:

use git diff to find the current changes
⚠ Vago

El subagente tiene que averiguar por su cuenta qué ficheros importan.

Description: "…You must tell the agent precisely which files you want it to review."

Prompt de entrada que escribe el principal:

Review these files: src/auth/session.ts,
src/auth/token.ts, src/api/login.ts
✓ Dirigido

La misma técnica funciona en cualquier subagente. Ejemplo: añadir "return sources that can be cited" a un subagente de búsqueda web hace que el principal incluya esa instrucción al delegar.

Las cuatro claves

Interactivo · toca cada clave

Controla cuándo se lanza el subagente y qué instrucciones recibe. Escríbela para dirigir las dos cosas — no solo para que se dispare, sino para que se dispare con el encargo correcto.

◈ La mejora individual más importante

Definir un formato de salida en el system prompt. Es la palanca del capítulo.

Hace dos cosas:

  1. Crea puntos de parada naturales — el subagente sabe que ha terminado cuando ha rellenado cada sección.
  2. Evita que corra demasiado tiempo — sin salida definida, los subagentes no saben decidir cuánta investigación es suficiente y tienden a correr mucho más de lo necesario.
Provide your review in a structured format:

1. Summary: Brief overview of what you reviewed and overall assessment
2. Critical Issues: Any security vulnerabilities, data integrity risks,
   or logic errors that must be fixed immediately
3. Major Issues: Quality problems, architecture misalignment, or
   significant performance concerns
4. Minor Issues: Style inconsistencies, documentation gaps, or
   minor optimizations
5. Recommendations: Suggestions for improvement, refactoring
   opportunities, or best practices to apply
6. Approval Status: Clear statement of whether the code is ready
   to merge/deploy or requires changes

Cuando un subagente descubre un workaround —resolver un problema de dependencias, ver que cierto comando necesita flags concretos— eso tiene que aparecer en el resumen que devuelve.

⚠ Si no

El hilo principal tiene que redescubrir las mismas soluciones, gastando tiempo y tokens.

Lo que quieres que aflore: problemas de setup o rarezas del entorno · workarounds descubiertos · comandos con flags especiales · dependencias o imports problemáticos.

La forma de conseguirlo es pedirlo explícitamente en el formato de salida:

7. Obstacles Encountered: Report any obstacles encountered during the
   review process. This can be: setup issues, workarounds discovered or
   environment quirks. Report commands that needed a special flag or
   configuration. Report dependencies or imports that caused problems.

Dale solo las herramientas que su trabajo requiere. Consigue dos cosas: evita efectos secundarios no deseados y clarifica el rol de cada subagente cuando tienes varios.

TipoHerramientasRazón
Investigación / solo lecturaGlob Grep ReadNo puede modificar ficheros accidentalmente
Revisor de código+ BashNecesita Bash para git diff y ver qué cambió — pero sigue sin necesitar Edit ni Write
Estilos / modificación+ Edit WriteAquí sí: su trabajo es cambiar tu código
◈ Juntándolo todo

Cada patrón es simple por separado, pero juntos convierten un subagente de "algo que vagamente intenta ayudar" en un trabajador enfocado y predecible que termina a tiempo y reporta con claridad.

Usar subagentes con criterio

¿Cuándo ayudan de verdad y cuándo estorban? La diferencia se reduce a una cosa: si el trabajo intermedio le importa o no a tu hilo principal.

Los subagentes funcionan mejor cuando la exploración está separada de la ejecución. Si cada paso depende de lo que descubrió el anterior, quieres ese trabajo en tu hilo principal. Si solo necesitas una respuesta y el viaje te da igual, delégalo.

Los tres casos donde brillan

Interactivo · toca cada caso

El caso de uso clásico. Investigar cómo funciona la autenticación en un codebase desconocido: tu hilo principal necesita saber dónde se valida el JWT, no ver cada fichero que se buscó.

El subagente lee decenas de ficheros, rastrea llamadas y explora rutas. Toda esa exploración se queda en su contexto. Tu hilo principal recibe:

JWT validation happens in middleware/auth.js line 42,
called from the Express router in route/api.js
Claude revisa código de forma más eficaz cuando el código se le presenta como escrito por otra persona.

Si construiste una feature a lo largo de muchos turnos con tu hilo principal, pedirle a ese mismo hilo que la revise suele producir feedback flojo: estuvo implicado en crearla, le cuesta verla con ojos frescos.

Un subagente revisor ve los cambios en un contexto separado: ejecuta git diff, lee los ficheros modificados y aplica sus criterios sin el historial de cómo se escribió.

✓ Ventaja de equipo

Esa separación te permite codificar los estándares de revisión del proyecto en su system prompt, garantizando criterios consistentes en todo el equipo.

El system prompt por defecto de Claude Code enfatiza respuestas concisas y centradas en código. Perfecto para programar, no para todo.

Copywriting

Instrucciones de tono, audiencia y estilo. El prompt por defecto tiende a escritura técnica concisa, que no es lo que quieres para una landing page o una campaña de email.

Estilos

Lo apuntas a los ficheros de tu design system. Al ejecutarse se cargan solos en su contexto: conoce tus variables de color, espaciados y patrones de componente antes de escribir una línea de CSS.

Los tres antipatrones

El coste de lanzar un subagente —perder visibilidad y comprimir los hallazgos en un resumen— solo compensa cuando hace algo que el hilo principal no puede.

Interactivo · por qué falla cada uno

Prompts del tipo "you are a Python expert" o "you are a Kubernetes specialist".

⚠ Por qué no aporta

Claude ya tiene ese conocimiento. No hay nada que un supuesto subagente experto pueda hacer que tu hilo principal no pueda hacer directamente.

Un flujo de tres agentes: uno reproduce el bug, otro lo depura, otro lo arregla.

⚠ Cuándo fallan

Los pipelines funcionan cuando las tareas son realmente independientes. Fallan cuando cada paso depende de descubrimientos del anterior — y arreglar bugs casi siempre es así. La información se pierde en el traspaso entre agentes.

Ese trabajo va en el hilo principal.

Un subagente que corre los tests oculta información que necesitas. Cuando fallan, quieres la salida completa para diagnosticar. Uno que devuelve "tests failed" te obliga a crear scripts de depuración adicionales para conseguir detalles que habrían estado visibles en la salida directa.

⚠ El dato

Las pruebas mostraron que el patrón de test runner fue el que peor rendimiento dio de todas las configuraciones.

◈ La regla de decisión

¿Importa el trabajo intermedio?

✓ Usa subagentes para
  • Investigación y exploración
  • Revisiones de código
  • Tareas que necesitan un system prompt a medida
✗ Evítalos para
  • Personas de "experto" que no añaden capacidad real
  • Pipelines multipaso donde cada paso depende del anterior
  • Ejecutar tests cuando necesitas la salida completa para depurar
