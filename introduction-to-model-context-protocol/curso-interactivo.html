El problema que resuelve

El enfoque tradicional te obliga a escribir a mano los esquemas y las funciones de cada integración.

⚠ El coste

Un chatbot de GitHub exigiría implementar herramientas para repositorios, pull requests, issues y proyectos. Eso crea una carga de mantenimiento en servicios complejos con muchas funcionalidades.

MCP traslada la definición y la ejecución de herramientas de tu servidor a un servidor MCP dedicado. Un servidor MCP es una interfaz a un servicio externo que envuelve su funcionalidad en herramientas ya construidas.

✓ El beneficio

Elimina la necesidad de que escribas y mantengas esquemas e implementaciones. Otro las escribe y las empaqueta en el servidor MCP.

Clientes MCP y el proyecto

Interfaz de comunicación entre tu servidor y el servidor MCP, que te da acceso a sus herramientas.

Agnóstico del transporte

Pueden hablar por stdin/stdout, HTTP o WebSockets. Lo habitual: ambos en la misma máquina por stdin/stdout.

Los cuatro mensajes

list tools request/result para pedir la lista · call tool request/result para ejecutar.

◈ El papel del cliente MCP

No ejecuta las herramientas él mismo. Actúa de intermediario: solo facilita la comunicación entre tu servidor y el servidor MCP, que es quien las ejecuta de verdad.

El proyecto del curso

Un chatbot de línea de comandos que implementa cliente y servidor, con documentos falsos guardados solo en memoria y dos herramientas: leer y actualizar el contenido de un documento.

ℹ Aviso de contexto real

Normalmente un proyecto implementa el cliente O el servidor, no ambos. Aquí se hacen los dos para aprender.

Montaje: descarga CLI_project.zip, extráelo, configura el .env con tu clave e instala dependencias. Ejecución: uv run main.py o python main.py. Aparece el prompt de chat y responde a consultas básicas.

Lección 3

Definir tools

El SDK de Python auto-genera los JSON Schema a partir de tus funciones decoradas. Adiós a escribirlos a mano.

✓ Lo que te ahorra el SDK

Genera el esquema desde la función, permite crear el servidor en una sola línea y elimina la escritura manual de esquemas.

El patrón

decorador → definición de función → tipado de parámetros → validación → lógica
  • Decorador @mcp.tool
  • Función con parámetros tipados
  • Field() de pydantic con description para describir cada argumento

Las dos herramientas del proyecto

Almacenamiento: un diccionario en memoria con doc_id como clave y el contenido como valor.

Manejo de errores: valida que el documento existe antes de operar.

Lección 4

Implementar un cliente

Una clase envoltorio alrededor de la sesión, que expone la funcionalidad del servidor MCP al resto de tu código.

Client Session

La conexión real al servidor MCP, del SDK de Python. Requiere limpieza de recursos al cerrar.

MCP Client

Clase envoltorio que gestiona conexión y limpieza, con connect, cleanup, async enter y async exit.

ℹ Práctica habitual

Envolver la client session en una clase mayor en vez de usarla directamente, para gestionar mejor los recursos.

async def list_tools(self):
    result = await self.session.list_tools()
    return result.tools

async def call_tool(self, tool_name, tool_input):
    return await self.session.call_tool(tool_name, tool_input)

El flujo de implementación

La aplicación pide la lista de herramientas para Claude.

El cliente llama a list_tools().

Claude selecciona una herramienta y aporta los parámetros.

El cliente llama a call_tool() para ejecutarla en el servidor.

Los resultados vuelven a Claude.

Probarlo: ejecuta mcp client.py directamente con un arnés de pruebas para verificar la conexión y el listado. Una vez implementado, lanza la CLI y prueba con algo como "what is contents of report.pdf document".

Lección 5

Resources

Funcionalidad del servidor MCP que expone datos a los clientes para operaciones de lectura.

Interactivo · los dos tipos
docs://documents

URI fija. Típico para listar los elementos disponibles.

documents/{doc_id}

URI parametrizada con comodines. Los parámetros de la URI se convierten automáticamente en argumentos con nombre de la función. Típico para traer uno solo.

✓ Patrón habitual

Un resource por cada operación de lectura distinta — listar elementos vs. traer uno.

El flujo

El cliente envía una petición de lectura con la URI.

El servidor MCP empareja la URI con la función del resource.

El servidor ejecuta la función y devuelve el resultado.

El cliente recibe los datos en el mensaje de resultado.

Definirlos y leerlos

En el servidor: decorador @mcp.resource con la URI —una dirección tipo ruta— y el MIME type. El SDK serializa automáticamente los valores devueltos a cadenas.

◈ Para qué sirve el MIME type

Es una pista para el cliente sobre el formato devuelto, para que sepa cómo deserializarlo. Por eso la lógica del cliente lo consulta.

async def read_resource(self, uri):
    result = await self.session.read_resource(AnyUrl(uri))
    resource = result.contents[0]
    if resource.mime_type == "application/json":
        return json.loads(resource.text)
    return resource.text

Dependencias: el módulo json y AnyUrl de pydantic para el tipado.

✓ El resultado que importa

Permite seleccionar documentos desde la CLI con las flechas y la barra espaciadora, y el contenido seleccionado se incluye automáticamente en los prompts.

Ya no hacen falta herramientas para leer el contenido durante el chat. Los datos llegan por otra vía — y ese contraste es justo lo que ordena el capítulo 7.

Lección 6

Prompts

Instrucciones ya escritas y probadas que los servidores MCP exponen a los clientes para tareas especializadas.

◈ El beneficio

Los autores del servidor crean prompts optimizados y probados para su dominio, en vez de dejar la calidad del prompt en manos del usuario final.

Los clientes los invocan mediante slash commands — por ejemplo /format.

Definirlos en el servidor

@prompt(name="format", description="rewrites document in markdown")
def format_document(doc_id: str) -> list[messages]:
    return [base.user_message(prompt_text)]

Decorador @prompt con nombre y descripción · la función recibe argumentos · devuelve una lista de mensajes en formato usuario/asistente, que se envían directamente a Claude.

Invocarlos desde el cliente

async def list_prompts(self):
    result = await self.session.list_prompts()
    return result.prompts

async def get_prompt(self, prompt_name, arguments):
    result = await self.session.get_prompt(prompt_name, arguments)
    return result.messages
ℹ El flujo de los argumentos

Argumentos del cliente → argumentos con nombre de la función → interpolados en el texto de la plantilla → array de mensajes para el modelo.

De punta a punta

El usuario escribe /format.

Selecciona un documento.

El servidor devuelve el prompt especializado con el ID interpolado.

El cliente lo envía a Claude.

Claude usa las herramientas para leer, reformatear y guardar el documento.

El propósito: encapsular la experiencia en prompt engineering del dominio dentro de servidores MCP especializados.

Las tres primitivas

Tools, resources y prompts se distinguen por quién decide cuándo se usan. Con eso, elegir deja de ser una duda.

PrimitivaQuién controlaA quién sirve
ToolsEl modelo — Claude decide cuándo ejecutarlasAl modelo
ResourcesEl código de la aplicación decide cuándo traer los datosA la aplicación
PromptsEl usuario, con un clic o un slash commandAl usuario
