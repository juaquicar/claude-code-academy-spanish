Introduction to Agent Skills

Una skill es un fichero markdown que le enseña a Claude cómo hacer algo una vez, y que Claude aplica automáticamente cuando viene al caso.

2campos obligatorios

◈ El problema que resuelven

Cada vez que le explicas a Claude los estándares de tu equipo, te estás repitiendo. En cada revisión de PR vuelves a describir cómo quieres el feedback. En cada commit le recuerdas tu formato.

Si te encuentras explicándole lo mismo a Claude una y otra vez, eso es una skill esperando a ser escrita.

Lo que las hace distintas

Claude Code tiene varias formas de personalizarse. Las skills son únicas porque son automáticas y específicas de una tarea.

Cuándo se cargaQuién la dispara
CLAUDE.mdEn todas las conversacionesSiempre está
SkillsBajo demanda, al coincidir con tu peticiónClaude, al reconocer la situación
Slash commandsAl invocarlosTú, escribiéndolos
✓ Por qué son baratas en contexto

Al arrancar, Claude solo carga el nombre y la descripción, no el contenido. Tu checklist de revisión de PR no tiene por qué estar en contexto mientras depuras: se carga cuando pides una revisión de verdad.

◈ La descripción lo es todo

Es el campo del que depende absolutamente todo el curso: decide si la skill se activa, mediante coincidencia semántica contra tu petición. Y cuando algo falla, el problema casi siempre está ahí — la lección 6 lo confirma.

Una buena descripción responde dos preguntas: qué hace la skill y cuándo debe usarla Claude.

Lección 115 min ▶ Vídeo original

¿Qué son las skills?

Carpetas de instrucciones y recursos que Claude Code puede descubrir y usar para resolver tareas con más precisión. Cada una vive en un fichero SKILL.md.

---
name: pr-review
description: Reviews pull requests for code quality. Use when reviewing PRs or checking code changes.
---

Bajo el frontmatter escribes las instrucciones reales: tu checklist de revisión, tus preferencias de formato, o lo que Claude necesite saber para esa tarea.

Dónde viven

Interactivo · personal vs. proyecto
~/.claude/skills/

Te siguen a todos tus proyectos: tu estilo de mensajes de commit, tu formato de documentación, cómo te gusta que te expliquen el código.

En Windows: C:/Users/<tu-usuario>/.claude/skills

<raíz-del-repo>/.claude/skills/

Cualquiera que clone el repo las obtiene automáticamente. Aquí viven los estándares de equipo: guías de marca de tu empresa, tipografías y colores para diseño web.

Se versionan junto al código, así que todo el equipo las comparte.

Cuándo usar skills

Funcionan mejor para conocimiento especializado que aplica a tareas concretas:

  • Estándares de revisión de código de tu equipo
  • Formatos de mensaje de commit que prefieres
  • Guías de marca de tu organización
  • Plantillas de documentación para tipos concretos de documento
  • Checklists de depuración para frameworks concretos
◈ La regla de oro

Si te encuentras explicándole lo mismo a Claude una y otra vez, eso es una skill esperando a ser escrita.

Crear tu primera skill

Una skill personal que enseña a Claude a escribir descripciones de PR en un formato consistente, y que funciona en todos tus proyectos.

Crea el directorio. El nombre debe coincidir con el de la skill:
mkdir -p ~/.claude/skills/pr-description

Crea el SKILL.md dentro, con el frontmatter y las instrucciones.

Reinicia Claude Code — las skills se cargan al arrancar.

Pruébala: haz cambios en una rama y di "write a PR description for my changes". El mismo formato siempre.

---
name: pr-description
description: Writes pull request descriptions. Use when creating a PR, writing a PR, or when the user asks to summarize changes for a pull request.
---

When writing a PR description:

1. Run `git diff main...HEAD` to see all changes on this branch
2. Write a description following this format:

## What
One sentence explaining what this PR does.

## Why
Brief context on why this change is needed

## Changes
- Bullet points of specific changes made
- Group related changes together
- Mention any files deleted or renamed

Cómo funciona el emparejamiento

Los cuatro pasos, del arranque a la activación

Al arrancar, Claude Code escanea cuatro ubicaciones buscando skills — pero solo carga el nombre y la descripción, no el contenido completo. Es un detalle importante.

Cuando envías una petición, Claude la compara con las descripciones de todas las skills disponibles.

◈ Es coincidencia semántica, no de palabras exactas

"explain what this function does" emparejaría con una skill descrita como "explain code with visual diagrams", porque la intención se solapa.

Encontrada la coincidencia, Claude te pide confirmación antes de cargarla. Ese paso te mantiene consciente de qué contexto está incorporando.

Tras confirmar, Claude lee el SKILL.md completo y sigue sus instrucciones.

Prioridad ante nombres iguales

Si clonas un repositorio con una skill que se llama igual que una tuya personal, ¿cuál gana? Toca cada nivel:

Interactivo · la jerarquía
✓ Cómo evitar conflictos

Usa nombres descriptivos. En vez de review, algo como frontend-review o backend-review.

⚠ El ciclo de vida, resumido

Actualizar → edita el SKILL.md. Eliminar → borra el directorio. En ambos casos, reinicia Claude Code para que surta efecto.

Configuración y skills multi-fichero

Los campos del frontmatter, cómo escribir descripciones que disparen de verdad, restringir herramientas, y organizar skills grandes sin llenar el contexto.

Constructor de SKILL.md

Interactivo · toca las opciones y mira el fichero

Los campos

CampoObligatorioDetalle
name✅Solo minúsculas, números y guiones. Máx. 64 caracteres. Debe coincidir con el nombre del directorio
description✅Máx. 1.024 caracteres. El campo más importante: es el que usa Claude para emparejar
allowed-tools—Restringe qué herramientas puede usar Claude con la skill activa
model—Qué modelo de Claude usar para la skill
◈ Escribir descripciones eficaces

Si alguien te dijera "tu trabajo es ayudar con la documentación", no sabrías qué hacer — Claude piensa igual. Una buena descripción responde dos preguntas:

① ¿Qué hace la skill? ② ¿Cuándo debe usarla Claude?

Si tu skill no se dispara cuando lo esperas, añade más palabras clave que coincidan con cómo formulas realmente tus peticiones. El lenguaje importa.

ℹ Si omites allowed-tools

No restringe nada: Claude usa su modelo de permisos normal.

Divulgación progresiva

Las skills comparten la ventana de contexto con tu conversación. Meterlo todo en un fichero de 2.000 líneas tiene dos problemas: ocupa mucho contexto y es incómodo de mantener.

La solución: instrucciones esenciales en SKILL.md, y el material detallado en ficheros aparte que Claude lee solo cuando hacen falta.

mi-skill/ ├── SKILL.md bajo 500 líneas ├── scripts/ código ejecutable ├── references/ documentación adicional └── assets/ imágenes, plantillas, datos

En SKILL.md enlazas los ficheros de apoyo con instrucciones claras de cuándo cargarlos.

Claude lee architecture-guide.md solo cuando alguien pregunta por el diseño del sistema. Es como tener un índice en la ventana de contexto en vez del documento entero.
◈ Regla del pulgar

Mantén SKILL.md por debajo de 500 líneas. Si lo superas, plantéate partir el contenido en ficheros de referencia.

Scripts

✓ Los scripts no consumen contexto

Se ejecutan sin cargar su contenido: el script corre y solo la salida consume tokens.

La instrucción clave que debes poner en tu SKILL.md: dile a Claude que ejecute el script, no que lo lea.

Especialmente útil para validación del entorno, transformaciones de datos que deben ser consistentes, y operaciones más fiables como código probado que como código generado.

Skills vs. otras funcionalidades

Claude Code ofrece cinco opciones de personalización. Resuelven problemas distintos, y saber cuándo usar cada una evita que construyas lo que no es.

FuncionalidadSe activa porDónde vive el trabajo
CLAUDE.mdSiempre — en cada conversaciónEl contexto actual
SkillsTu petición — request-drivenEl contexto actual
SubagentesDelegación explícitaUn contexto separado
HooksEventos — event-drivenFuera de la conversación
Servidores MCPHerramientas externasOtra categoría entera
Interactivo · las tres comparaciones que importan

CLAUDE.md se carga en todas las conversaciones, siempre. Las skills, bajo demanda.

Usa CLAUDE.md para
  • Estándares de proyecto que siempre aplican
  • Restricciones como "nunca modifiques el esquema de la base de datos"
  • Preferencias de framework y estilo de código
Usa skills para
  • Experiencia específica de una tarea
  • Conocimiento que solo a veces es relevante
  • Procedimientos que ensuciarían todas las conversaciones

Las skills añaden conocimiento a tu conversación actual. Los subagentes corren en un contexto separado: reciben una tarea, trabajan solos y devuelven resultados. Están aislados.

Usa subagentes cuando
  • Quieres delegar a un contexto separado
  • Necesitas acceso a herramientas distinto
  • Quieres aislamiento del trabajo delegado
Usa skills cuando
  • Quieres mejorar el conocimiento para la tarea actual
  • La experiencia aplica a lo largo de la conversación

Los hooks disparan por eventos — un linter en cada guardado, validación antes de ciertas llamadas. Las skills disparan por peticiones.

Usa hooks para
  • Operaciones en cada guardado
  • Validación antes de llamadas concretas
  • Efectos secundarios automáticos
Usa skills para
  • Conocimiento que informa cómo atiende las peticiones
  • Directrices que afectan a su razonamiento
◈ Un montaje típico usa las cinco

CLAUDE.md estándares siempre activos · skills experiencia por tarea, bajo demanda · hooks operaciones por evento · subagentes contextos aislados · MCP herramientas externas.

Cada una gestiona su especialidad. No fuerces todo dentro de las skills cuando otra opción encaja mejor.

Compartir skills

Una skill de revisión de PR que solo usas tú es útil. Esa misma skill compartida con todo tu equipo estandariza la revisión de código.

Interactivo · los tres métodos de distribución

El método más simple: las pones en .claude/skills y cualquiera que clone el repo las obtiene automáticamente, sin instalación extra. Cuando publicas actualizaciones, todos las reciben en el siguiente pull.

Funciona bien para: estándares de código del equipo · flujos específicos del proyecto · skills que referencian la estructura de tu codebase.

El directorio .claude contiene tus agentes, hooks, skills y settings — todo versionado y compartido por flujos de Git normales.

En tu proyecto de plugin, crea un directorio skills que siga una estructura similar a la de .claude: cada skill en su propia carpeta con un SKILL.md dentro.

Tras distribuirlo a un marketplace, otros usuarios pueden descubrirlo e instalarlo. Es lo mejor cuando tus skills no son demasiado específicas del proyecto y pueden servir a gente más allá de tu equipo.

Los administradores despliegan skills a toda la organización. Máxima prioridad: sobrescriben personales, de proyecto y de plugin con el mismo nombre.

El fichero de managed settings soporta strictKnownMarketplaces, para controlar desde dónde se instalan plugins:

"strictKnownMarketplaces": [
  {
    "source": "github",
    "repo": "acme-corp/approved-plugins"
  },
  {
    "source": "npm",
    "package": "@acme-corp/compliance-plugins"
  }
]
◈ Cuándo

Estándares obligatorios, requisitos de seguridad, flujos de cumplimiento y prácticas que deben ser consistentes. La palabra clave es "deben".

Skills y subagentes

⚠ Esto sorprende a mucha gente

Los subagentes NO ven tus skills automáticamente. Cuando delegas una tarea a un subagente, arranca con un contexto limpio y nuevo.

Tipo de agente¿Puede usar skills?
Integrados (Explorer, Plan, Verify)✗ No pueden acceder a skills en absoluto
Propios, definidos por ti✓ Sí, pero solo si las listas explícitamente

Y un matiz de comportamiento: en un subagente las skills se cargan al arrancar, no bajo demanda como en la conversación principal.

Añade un fichero markdown en .claude/agents — o usa /agents para crearlo de forma interactiva. El fichero incluye un campo skills:

---
name: frontend-security-accessibility-reviewer
description: "Use this agent when you need to review frontend code for accessibility..."
tools: Bash, Glob, Grep, Read, WebFetch, WebSearch, Skill...
model: sonnet
color: blue
skills: accessibility-audit, performance-check
---

El orden: primero asegúrate de que las skills existen en .claude/skills, luego crea el subagente o añade el campo a uno existente.

Este patrón va muy bien cuando quieres delegación aislada con experiencia concreta, cuando distintos subagentes necesitan distintas skills (revisor de frontend vs. de backend), y cuando quieres imponer estándares en el trabajo delegado sin depender de los prompts.

Solución de problemas

Cuando las skills no funcionan, el problema cae casi siempre en una de unas pocas categorías. La buena noticia: la mayoría de arreglos son directos.

✓ Empieza siempre por el validador

El comando verificador de agent skills — se instala fácil con uv. Detecta problemas estructurales antes de que pierdas tiempo depurando otras cosas.
